## Новые изменения

- Проверка ролей реализована триггером `cgb_validate_user_role`: разрешены базовые `admin`/`ss`/`user` и существующие ключи `custom_roles`. Неизвестная роль, несуществующий ID или несовместимая базовая роль отклоняются. Первый admin по-прежнему создаётся владельцем БД, а не публичным RPC.
- Добавлен индекс запусков тестов по аккаунту и подсчёт попыток по `user_id` наряду с прежними идентификаторами. Пользователь без записи `user_roles` не может запускать тест как авторизованный сотрудник; удалённая роль также запрещает завершать его авторизованную сессию. Анонимные кандидаты продолжают проходить тесты.
- Проверки лимита и блокировки перенесены из предварительных браузерных запросов в `cgb_start_test`. Отозвано клиентское выполнение `count_test_attempts` и `check_test_blocked`; внутренние вызовы серверных функций сохранены. Страница получает результат проверки от сервера.
- В исходном шаблоне `SUPABASE-SETUP.sql` также убрано безусловное анонимное чтение всех таблиц. Публичные материалы открывает завершающий блок точных политик.
- Новый блок синхронизирован с полным SETUP, FIX, обоими UPDATE и обёрткой `supabase-migration.sql`, чтобы повторное применение старого обновления не отменяло защиту.
- Проверка PostgreSQL-комплекта исключает `updv3` из поиска рабочих файлов.

## Применение пакета

В `updv3` находятся 11 файлов с исходными относительными путями; перечень и контрольные суммы — в `docs/SECURITY-UPDATE-V3-FILES.json`. В GitHub **Add files → Upload files** загрузите содержимое `updv3` в корень репозитория, сохраняя вложенность, после предыдущих обновлений. Саму папку `updv3` внутрь проекта на GitHub загружать не нужно. `upd` и `updv2` сохранены.

Загрузка SQL-файлов на GitHub сама по себе не меняет права рабочей БД. **Все SQL этого пакета относятся к legacy Supabase. На автономном PostgreSQL их не выполнять:** они используют `auth.uid()`, роли Supabase и Storage. Для оставшейся Supabase-версии полный `SECURITY-HARDENING.sql` применяется владельцем БД после резервного копирования и вместе с соответствующим frontend. Исходников автономного API в этой папке нет, поэтому его исправление или развёртывание этим пакетом не заявляется.

## Сохранённые ограничения публичных форм

ФИО, Static ID и Discord вводит сам отправитель. Они не доказывают личность, позволяют указать чужие сведения и обходить ограничения сменой значений. Даже вошедший пользователь может выйти и воспользоваться публичным тестом. Поэтому привязка авторизованных попыток к аккаунту не является полным устранением пункта 4.

Надёжный лимит на человека и блокировку конкретного человека можно обеспечить только подтверждённой личностью либо индивидуальным допуском, выданным доверенным сервером. Публичный формат, постоянные ссылки и самозаявленные идентификаторы сохранены по выбору владельца; обязательный вход, новые аккаунты для кандидатов и отсутствующий сервер в рамках этого обновления не вводились. Ограничения частоты публичных форм по введённому статику также не заменяют контроль источника запроса.
