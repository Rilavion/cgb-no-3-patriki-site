# Проверка кода и безопасности — 2 октября 2026

Проверен предоставленный снимок `cgb-no-3-patriki-site-main`: 45 HTML-страниц, 45 собственных JavaScript-файлов, SQL-скрипты, конфигурация Nginx и зависимости. Проверка выполнялась локально. Рабочая база Supabase и действующий сервер не изменялись. Тексты страниц и оформление намеренно не редактировались; комментарии в новый код не добавлялись.

## Исправленные проблемы

| Риск | Что обнаружено | Исправление |
| --- | --- | --- |
| Критический | `write_auth` разрешал любому авторизованному пользователю менять практически все таблицы | Права проверяются в PostgreSQL по разделу и операции. Старые политики удаляются, добавляются ограничивающие политики, которые нельзя обойти добавлением разрешающей политики |
| Критический | `staff_upsert_role` разрешал захват администратора при отсутствии других администраторов | Назначение ролей допускается только действующему администратору, включая старые перегрузки RPC |
| Критический | Браузер получал правильные ответы и передавал собственные баллы, процент и признак сдачи | Вопросы выдаются без ключей ответов. Сервер выбирает вопросы, сохраняет их снимок, время начала и порог, рассчитывает результат и создаёт очередь отправки |
| Высокий | Открытый `request_test_result` позволял отправлять результаты в произвольный Discord-канал | Обычное завершение теста само создаёт одну отправку в настроенный сервером канал. Повторная отправка разрешена сотруднику с `tests:edit` |
| Высокий | `SECURITY DEFINER` обходил RLS, а права `PUBLIC EXECUTE` сохранялись для служебных функций | Введён явный список доступных RPC; внутренние функции и старый `submit_test_attempt` закрыты. Служебные RPC отдельно проверяют полномочия |
| Высокий | Жалобы, заявки, премии, попытки, блокировки и служебные справочники читались анонимно | Открыты только необходимые публичные материалы и формы. Служебные записи доступны по правам раздела; пользователь видит собственную запись роли |
| Высокий | Составная роль могла получить лишние права через одновременно выбранную кастомную и базовую роль | При наличии `custom_role_id` используется только выбранная роль. Клиентский обход для `ab_operator` удалён; доступ определяется явными permissions |
| Высокий | Неэкранированный запрос и данные индекса вставлялись в HTML поиска | Добавлено экранирование текста и атрибутов, запрещена навигация на исполняемые URL, исправлен объект группировки |
| Высокий | Ссылки доказательств, материалов и уведомлений могли содержать `javascript:` и другие исполняемые схемы | URL проходят проверку схемы; уведомления ведут только на тот же сайт. У предпросмотра материалов убрано сочетание `allow-scripts` с `allow-same-origin` |
| Высокий | Общие политики Storage могли разрешать запись и удаление фотографий любой учётной записи | Ограничивающие политики привязаны к `composition:edit` и `autopark:edit`; для двух bucket заданы MIME-типы изображений и лимит размера |
| Средний | Публичные формы принимали запросы без серверной проверки включённости и размера данных | Проверяются форма, допустимый вид заявки, ФИО, формат статика, размер JSON и частота обращений по указанному статику |
| Средний | Публичная подача запроса наказания могла получить слишком широкие права на дисциплинарный реестр | `vp_request:submit` разрешает только новую запись `pending` от текущего пользователя без решения, удаления и срока действующего наказания. Рассмотрение имеет отдельное право |
| Средний | Автор операции и имя для журнала задавались браузером | Триггер подставляет текущего пользователя и имя из `user_roles` для изменяемых полей авторства, а также серверное время |
| Средний | Служебные справочники могли сохраняться в общем кэше после выхода или смены пользователя | Кэш привязан к пользователю, справочники перенесены в sessionStorage, кэш очищается при смене сессии и роли; отказ API не заменяется старым справочником |
| Средний | Значения фильтра сброса попыток вставлялись в PostgREST `or` без quoting | Добавлено экранирование значений фильтра |
| Средний | Ошибка назначения роли пыталась переназначить переменную `const` | Исправлено на `let` |
| Средний | Загрузчик Supabase автоматически исполнял код сторонних CDN | Используется уже поставленный локальный `vendor/supabase.js` |
| Функциональный | 815 ссылок указывали на отсутствующий каталог `assets` | Исправлены пути HTML, JavaScript и Nginx под фактическую структуру `public` |
| Функциональный | SQL тестов не содержал используемых редактором полей | Добавлены совместимые поля вопросов, названия категорий и тип блокировки без удаления данных; снята зависимость добавления блокировки от отсутствующего уникального индекса |

Ограничивающие политики соединяются с разрешающими через AND: это важно, поскольку разрешающие политики обычно объединяются через OR. Основание: [PostgreSQL CREATE POLICY](https://www.postgresql.org/docs/17/sql-createpolicy.html). Отзыв выполнения функций затрагивает также `PUBLIC`, а не только `anon`: [Supabase — Database Functions](https://supabase.com/docs/guides/database/functions).

## Проверки

- Статическая проверка: 45 HTML-страниц, 45 JavaScript-файлов; ошибок и предупреждений нет.
- 78 проверок на локальном PostgreSQL через PGlite. Supabase-роли, `auth.uid()`, Storage и публикация воспроизведены тестовым окружением.
- Проверены запрет прямой записи, приватность записей, делегированные права, отсутствие захвата администратора, закрытие старого RPC баллов, серверная оценка, повторное завершение, истечение времени, привязка сессии к пользователю и одна отправка результата.
- Проверены повторный запуск миграции, всех четырёх старых обновлений и `supabase-migration.sql`, добавление старой разрешающей политики и работа сервисной роли бота.
- Проверено, что `tests:view` не раскрывает ключи ответов, а `vp_request:submit` не позволяет сразу создать действующее наказание.
- `npm audit --package-lock-only`: известных уязвимостей в зарегистрированной npm-зависимости тестов не обнаружено. Эта проверка не распространяется на вручную поставленные файлы `public/vendor`.

Для повторения: `npm ci`, затем `npm run check` и `npm run check:security`. Среда проверки: Node.js 24.18.1, PGlite 0.5.8. Тесты создают отдельную локальную базу в памяти и не подключаются к рабочему Supabase.

## Применение

1. В корне репозитория GitHub откройте **Add files → Upload files**. Перетащите содержимое `upd`, сохраняя вложенные каталоги. Не загружайте сам каталог `upd` как новый каталог проекта. Файлы предназначены для замены по существующим путям; перечень находится в `docs/SECURITY-UPDATE-FILES.json`.
2. Перед изменением рабочей БД сохраните её резервную копию. На время одновременного обновления frontend и SQL поставьте сайт на обслуживание: новый frontend использует новые RPC.
3. Для уже существующей полной базы выполните целиком `database/legacy-supabase/SECURITY-HARDENING.sql` в Supabase SQL Editor от владельца проекта. Загрузка SQL на GitHub сама по себе не изменяет права базы. Если исходная база не содержит таблицы портала, сначала нужен полный `SUPABASE-SETUP.sql`; он уже содержит этот блок защиты. Сокращённый `supabase-migration.sql` не создаёт всю схему портала.
4. Разверните изменённый `public` и конфигурацию Nginx. На сервере проверьте конфигурацию через `nginx -t` перед её перезагрузкой. Nginx в локальной Windows-среде не запускался.
5. Проверьте вход, назначенные permissions, подачу каждой формы, редактирование разделов соответствующими ролями, завершение теста и отправку ботом. Правильные ответы доступны редакторам и сотрудникам с `tests:stats`, но не одному лишь `tests:view`. Право запроса наказания теперь требует явного `vp_request:submit`.

У новых и неизвестных таблиц нет доступа обычных пользователей по умолчанию. Неизвестные RPC и представления закрыты для клиентских ролей. Если рабочая база содержит дополнительные модули, которых нет в предоставленных исходниках, их права нужно добавить явно после проверки.

## Границы проверки и оставшиеся риски

- Исходников API, Discord-бота и Telegram-воркера в папке нет. Упомянутые в документации серверные маршруты, включая `/api/admin/users/delete`, проверить нельзя. На них должна независимо проверяться роль пользователя; скрытая кнопка или Nginx-прокси этого не обеспечивают.
- Нет выгрузки схемы и политик рабочей базы. Локальная проверка не подтверждает, что миграция уже применена или что реальные таблицы, триггеры и внешние интеграции полностью совпадают с SQL-файлами.
- Публичные формы и тесты продолжают принимать введённые ФИО, статик и Discord. Эти значения не подтверждают личность: можно указать чужой идентификатор или менять его для обхода ограничений. Ограничение частоты по статику не заменяет CAPTCHA, проверенный Discord-вход и серверный лимит по источнику запроса. Для устранения этого риска нужен отсутствующий в снимке сервер авторизации участников.
- Сервисная роль бота намеренно обходит RLS. Её ключ нельзя размещать в frontend. В доступном конфиге указан publishable-ключ, который не является сервисным секретом.
- Ограничения MIME и размера не являются проверкой содержимого файла или антивирусным сканированием. В конфигурации Nginx `/media` ограничен безопасными типами и sandbox, но отдельный обработчик загрузки отсутствует и не проверялся.
- Публичные изображения, уже выданные клиенту записи и ранее сохранённые копии невозможно отозвать задним числом. Исправление ограничивает последующие обращения и очищает известные кэши приложения.
- Самописные SQL-функции, добавленные только в рабочую базу, не исследованы по содержимому. Неизвестные клиентские RPC закрываются миграцией, но доступ сервисных ролей требует отдельной проверки серверного кода.
- Полная гарантия отсутствия уязвимостей из одного снимка исходников невозможна. Результат этой проверки — конкретные исправления и воспроизводимые тесты, а не подтверждение безопасности действующей инфраструктуры.
