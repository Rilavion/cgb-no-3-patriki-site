## 1. НАЗНАЧЕНИЕ И СОСТАВ ПРОЕКТА

ЦГБ №3 - веб-портал игровой медицинской организации проекта RMRP. Он объединяет публичную информационную часть, внутренний кабинет сотрудников, кадровые и медицинские заявки, жалобы и дисциплинарный реестр, проверки АБ, тестирование, поставки, премирование, документы, состав организации и интеграции с Discord и Telegram.

Проект состоит из пяти логических компонентов:

1) Статический frontend сайта - HTML, CSS и JavaScript, который Nginx отдаёт браузеру.
2) Слой данных текущей опубликованной версии - Supabase Auth, PostgREST, Realtime и Storage.
3) Подготовленный серверный API автономной версии - Node.js/Express между браузером и PostgreSQL.
4) Discord-бот - получает и отправляет рабочие сообщения, синхронизирует сервер Discord с БД.
5) Telegram-воркер - отправляет только уведомления по зарегистрированным темам частной Telegram-группы.

Папка `cgb-no-3-patriki-site` содержит структурированный снимок статических файлов рабочего VPS: 45 рабочих HTML-страниц в `public`, 47 JavaScript-файлов с учётом нового асинхронного ядра, 2 CSS-файла, изображения интерфейса, устава, состава и автопарка. Файлы с суффиксами `.bak-*` и стандартная страница Nginx перенесены в `archive/legacy-root` и не подключаются рабочими страницами.

Важно различать два состояния проекта:

- текущий снимок frontend продолжает обращаться к Supabase через `public/assets/js/core/config.js`, `public/assets/js/core/supabase-loader.js` и локальную сборку `public/assets/vendor/supabase.js`;
- рядом подготовлены схема автономного PostgreSQL, серверный API, PostgreSQL-версия Discord-бота, Telegram-воркер, Nginx-конфигурация и средства переноса данных;
- полное переключение произойдёт только после развёртывания новой БД, импорта данных и замены клиентского адаптера Supabase на API-совместимый слой.

## 2. ТЕХНОЛОГИЧЕСКИЙ СТЕК

### 2.1. Клиентская часть

- HTML5 - отдельный HTML-файл на каждый раздел.
- CSS3 - общий style.css и отдельный docs-editor.css.
- JavaScript без frontend-фреймворка.
- DOM API - построение карточек, таблиц, форм, модальных окон и редакторов.
- Fetch API - обращения к серверным маршрутам.
- LocalStorage - пользовательские настройки оформления, звука, уведомлений и черновики.
- Canvas API - фоновые эффекты и подготовка изображений.
- html2canvas - экспорт состава, статистики, услуг и документов в PNG.
- Google Fonts - Cormorant Garamond и Inter.

Frontend не использует React, Vue, Angular, TypeScript, Webpack или Vite. Сборка перед публикацией не требуется. Nginx отдаёт готовые HTML, CSS, JavaScript и изображения.

### 2.2. Текущий слой данных рабочего снимка

- Supabase JavaScript SDK.
- Supabase Auth - вход по email и паролю, восстановление сессии.
- PostgreSQL внутри Supabase - прикладные таблицы и функции.
- PostgREST - select/insert/update/delete/upsert и RPC.
- Supabase Realtime - события отдельных таблиц.
- Supabase Storage - фотографии состава и автопарка.
- Row Level Security - серверные ограничения текущей Supabase-версии.

### 2.3. Целевая автономная база данных

- PostgreSQL 15 или новее.
- Схема public из postgres-migration/01-schema.sql.
- 63 уникальные прикладные и служебные таблицы.
- PostgreSQL functions для сложных атомарных операций.
- Триггеры updated_at, Telegram-очередей и cgb_changes.
- LISTEN/NOTIFY cgb_changes для серверных процессов.
- отдельные роли подключения cgb_api, cgb_bot и cgb_telegram;
- полный отказ целевой версии от Supabase Auth, PostgREST, Realtime и Storage.

### 2.4. Серверный API PostgreSQL-версии

Папка postgres-api содержит отдельное приложение Node.js 20.11+:

- Express 5.1 - HTTP API;
- pg 8.16 - пул соединений PostgreSQL;
- bcryptjs - хеширование паролей;
- jsonwebtoken - access-токены;
- crypto и таблица refresh_tokens - обновляемые сессии;
- helmet - HTTP-заголовки;
- express-rate-limit - ограничение попыток входа;
- dotenv - серверная конфигурация;
- файловое хранилище VPS для фотографий состава и автопарка.

API слушает только 127.0.0.1:8787. Nginx публикует его по /api/v1/. Маршрут /media/ отдаёт изображения из /var/lib/cgb-storage с длительным кэшированием.

### 2.5. Discord-бот

- Node.js 18.17+; рекомендуемая версия - Node.js 20 LTS;
- discord.js 14;
- pg 8;
- dotenv;
- отдельное подключение DATABASE_URL от роли cgb_bot;
- Discord Gateway intents для сообщений, участников, ролей и реакций;
- периодический опрос очередей и LISTEN/NOTIFY cgb_changes;
- systemd или другой постоянный менеджер процесса.

Discord-бот не подключается к HTML напрямую. Страница сохраняет действие в БД через текущий Supabase-слой либо целевой API, а бот читает эту запись, публикует Discord Embed и возвращает в БД ID сообщения и статус доставки.

### 2.6. Telegram-воркер

- Python 3.11+;
- psycopg 3;
- стандартные urllib, threading, signal, zoneinfo и json;
- Telegram Bot API;
- отдельное подключение DATABASE_URL от роли cgb_telegram;
- опрос telegram_notifications, по умолчанию каждые 4 секунды;
- heartbeat в telegram_bot_status;
- работа с forum topics частной Telegram-группы.

Telegram-бот является только уведомителем. Он не управляет сайтом, не меняет решения и не связан напрямую с Discord-ботом. Оба процесса независимо читают предназначенные им данные из одной PostgreSQL.

### 2.7. Веб-сервер и инфраструктура

- VPS под Linux;
- Nginx - статический сайт, маршрутизация API и медиа;
- HTTPS и сертификаты Let's Encrypt/Certbot;
- systemd-службы для API, Discord-бота и Telegram-воркера;

## 4. АВТОРИЗАЦИЯ, ПОЛЬЗОВАТЕЛИ И РОЛИ

### 4.1. Вход

Форма входа принимает email и пароль. auth.js получает сессию, затем обязательно проверяет наличие user_id в user_roles. Если запись роли отсутствует, сессия отклоняется и пользователь выходит. Это не позволяет войти удалённому из списка пользователю, даже если старая запись авторизации ещё существует.

### 4.2. Таблицы ролей

- user_roles - user_id, ключ роли, отображаемое имя, custom_role_id и даты.
- custom_roles - ключ, название, цвет, описание, base_role, порядок и permissions JSON.

### 4.3. Проверка доступа

В HTML используются атрибуты вида:

data-perm="requests:review"

roles-engine.js разбивает разрешение на раздел и действие и вызывает can(section, action). Администратор проходит любую проверку. Остальные роли получают разрешения из custom_roles.permissions.

### 4.4. Базовые состояния интерфейса

- cgb-is-logged - пользователь вошёл;
- cgb-is-admin - роль admin;
- cgb-is-ss - роль старшего состава;
- cgb-is-staff - admin или ss.

### 4.5. Группы разрешений

- заявления: просмотр, редактирование, удаление;
- жалобы: просмотр, рассмотрение, форма, настройки;
- реестр нарушений: просмотр, добавление, редактирование и снятие;
- заявки сотрудников: просмотр, рассмотрение, настройки;

## 6. УВЕДОМЛЕНИЯ ВНУТРИ САЙТА

## 10. ЦЕЛЕВОЙ HTTP API

### 10.1. Авторизация

- POST /api/v1/auth/login - email/password, bcrypt и выдача access/refresh;
- POST /api/v1/auth/refresh - проверить refresh_tokens и обновить access;
- POST /api/v1/auth/logout - отозвать refresh-token;
- GET /api/v1/auth/session - получить текущую сессию;
- PATCH /api/v1/auth/user - изменить пароль или user_metadata;
- GET /api/v1/auth/admin/users - список пользователей для admin;
- POST /api/v1/auth/admin/users - создать пользователя и назначить роль;
- DELETE /api/v1/auth/admin/users/:id - удалить пользователя и его роль;
- GET /api/v1/health - проверить БД и API.

Удалённый пользователь не может продолжать вход: API проверяет users.disabled и обязательную строку user_roles при login и refresh. Удаление пользователя удаляет роль и аккаунт, поэтому старый refresh-token перестаёт давать сессию.

### 10.2. Данные и RPC

- POST /api/v1/db/query - разрешённые select/insert/update/delete/upsert;
- POST /api/v1/db/rpc/:name - разрешённые PostgreSQL functions;
- белый список TABLES ограничивает доступные таблицы;
- PUBLIC_READ задаёт публично читаемые справочники;
- ADMIN_TABLES требует роль admin;
- site_data дополнительно проверяет разрешение конкретного ключа;
- каждая транзакция устанавливает cgb.user_id для серверных функций.

Query compiler поддерживает безопасные идентификаторы, параметры, фильтры, сортировку, диапазоны, count и returning. SQL из браузера как произвольная строка не исполняется.

### 10.3. Файловое API

- PUT /api/v1/storage/:bucket/*object - загрузка до 25 МБ;
- DELETE /api/v1/storage/:bucket - удаление списка объектов;
- /media/* - публичная раздача сохранённых файлов;
- разрешённые bucket: composition-photos и autopark-photos;
- разрешённые форматы: JPEG, PNG, WebP и GIF;
- нормализация пути не допускает выход за STORAGE_ROOT;
- временный файл переименовывается в конечный после полной записи.

Основные переменные API: DATABASE_URL, JWT_SECRET, PUBLIC_ORIGIN и STORAGE_ROOT. Дополнительно используются PORT, PGSSL, PGPOOL_MAX, JWT_TTL, REFRESH_DAYS и TRUST_PROXY.

- ✅ - выполнено;
- ❌ - не выполнено;

- 🚫 - не доставлено;
- 🔄 - заменено.

Сайт выбирает каналы и роли из справочников, которые бот сохраняет в БД. При изменении настройки страница сохраняет Discord Snowflake ID; следующая публикация бота использует новое значение. Прямого вызова Discord API из браузера нет.

## 14. NGINX, URL И ЗАПУСК СЕРВИСОВ

Рабочая конфигурация cgb3-domain.conf:

- / перенаправляется на содержимое index.html без отображения имени файла;
- запрос /index.html перенаправляется на /;
- /composition и /composition.html перенаправляются на /team;
- URL с .html перенаправляются на чистый адрес;
- location / сначала ищет файл, каталог, затем соответствующий .html;
- /tests отдаёт tests.html с отключённым кэшированием;
- /api/v1/ проксируется на 127.0.0.1:8787;
- /media/ отображает /var/lib/cgb-storage/;
- auth.js, roles-engine.js и будущие database-*.js не кэшируются;
- `/assets/ustav/` кэшируется на 30 дней;
- максимальный размер тела API - 25 МБ;
- HTTPS обслуживается сертификатами Certbot.

Постоянные процессы:

- cgb-postgres-api.service - Node.js API от пользователя cgb-api;
- Discord-бот - Node.js-процесс от отдельного пользователя;
- cgb-telegram.service - Python-воркер от пользователя cgbtelegram;
- каждый процесс имеет собственный DATABASE_URL и перезапускается systemd.

Frontend отдельного процесса не имеет: это статические файлы из `public`, который Nginx использует как document root.

## 15. КОМПЛЕКТ МИГРАЦИИ НА POSTGRESQL

Папка postgres-migration содержит:

- 01-schema.sql - целевая структура, функции, триггеры и совместимость;
- 02-runtime-grants.sql - runtime-роли и права;
- export-supabase.mjs - экспорт таблиц и Storage из Supabase;
- import-postgres.mjs - импорт в автономный PostgreSQL;
- verify-postgres.mjs - сверка количества строк и основных связей;
- set-user-password.mjs - назначение автономного пароля;
- check-site.mjs - проверка ссылок frontend на таблицы/RPC;
- metadata.mjs - общие списки и сведения миграции;
- build-schema.py - построение итоговой схемы из исходных SQL;
- package.json/package-lock.json - Node.js-зависимости инструментов.

Подготовленная схема предусматривает отдельные runtime-подключения:

- cgb_api - серверный API сайта;
- cgb_bot - Discord-бот;
- cgb_telegram - Telegram-уведомитель.

Все три роли работают с одной БД, но не используют один общий пароль и не должны заменять друг друга.

## 16. ФАКТИЧЕСКОЕ ТЕХНИЧЕСКОЕ СОСТОЯНИЕ

Готово в текущем комплекте:

- полный снимок статического сайта с VPS;
- актуальная логика 46 страниц;
- текущая рабочая Supabase-интеграция;
- схема автономного PostgreSQL;
- функции заявок, жалоб, тестов, поставок, Telegram и уведомлений БД;
- Node.js API с автономной авторизацией и файловым хранилищем;
- PostgreSQL-версия Discord-бота;
- PostgreSQL-версия Telegram-воркера;
- Nginx-маршруты /api/v1 и /media;
- миграционные и проверочные инструменты.

Ещё не является выполненным переключением:

- файлы сайта в cgb-no-3-patriki-site по-прежнему подключают Supabase SDK;
- auth.js создаёт window.supabase.createClient из SUPABASE_CONFIG;
- 51 HTML/JS-файл содержит обращения или совместимые названия Supabase;
- в каталоге снимка отсутствуют database-config.js, database-loader.js и database-client.js, хотя Nginx уже предусматривает для них отдельное кэширование;
- новый PostgreSQL-хост и рабочие строки подключения ещё не указаны;
- данные и файлы ещё должны быть экспортированы, импортированы и сверены;
- после создания API-совместимого клиентского адаптера HTML-страницы должны переключиться с supabase-loader.js/config.js на автономный слой.

Поскольку прикладные модули используют общий интерфейс client.from(...), client.rpc(...), client.storage и auth, целевая стратегия - дать frontend совместимый клиент поверх /api/v1, а не переписывать каждую бизнес-страницу целиком.

## 17. ОСНОВНЫЕ СКВОЗНЫЕ СЦЕНАРИИ

### 17.1. Заявка сотрудника

Страница формы → проверка полей → submit_request → requests → Discord-бот публикует Embed и 🕒 → оператор рассматривает requests-review.html → статус и комментарий сохраняются → бот меняет реакцию и отправляет вердикт → Telegram-триггер при включённом маршруте создаёт отдельное уведомление.

### 17.2. Электронное заявление из Discord

Сообщение в настроенном канале → parser.js Discord-бота → applications → apps.html → принятие/отказ/архив → applications обновляется → бот меняет реакцию исходного сообщения и при необходимости отправляет карточку результата → событие отображается в журнале и уведомлениях сайта.

### 17.3. Тест

tests.html → test.html → проверка блокировки и числа попыток → ответы и порядок → submit_test_attempt → test_attempts → test_result_requests → Discord-бот публикует итог → Telegram-триггер отправляет только уже вычисленный вердикт → администратор может открыть детали, скорректировать результат, сбросить попытки или повторить пинг.

### 17.4. Жалоба и взыскание

complaints.html → submit_complaint → complaints → Discord-уведомление → complaints-review.html → решение → complaint_history и при наказании violations_registry → Discord-вердикт/приказ → автоматический срок либо ручное снятие → violations_history и уведомление о снятии.

### 17.5. Состав Discord и проверки АБ

Discord Gateway → синхронизация участников/ролей → ds_members/ds_roles → vp.html группирует сотрудников → проверяющий выставляет документы и доказательства → vp_checks → архив vp_archive → vp_report_requests → Discord-бот публикует многочастный отчёт.

### 17.6. Изображение состава или автопарка

Пользователь выбирает файл → frontend проверяет/обрабатывает изображение → текущая версия загружает в Supabase Storage, целевая версия отправляет PUT /api/v1/storage → БД сохраняет URL → браузер загружает изображение из Storage либо /media → полноразмерный просмотр и PNG-экспорт не создают дополнительной записи.

### 17.7. Управление доступом

Администратор создаёт пользователя → сервер создаёт users/Auth и user_roles → roles-engine получает custom_roles.permissions → data-perm открывает допустимые действия → серверный слой повторно проверяет пользователя и необходимые права → удаление user_roles/users немедленно лишает пользователя следующего входа и обновления сессии.
