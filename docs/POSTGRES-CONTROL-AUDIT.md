# Контрольная проверка PostgreSQL-версии — 2 октября 2026

## Итог

Предоставленная папка не проходит проверку готовности автономного PostgreSQL-комплекта. Это вывод о доступных исходниках, а не о состоянии опубликованного сайта. Рабочая база и сервер не изменялись. Тексты и оформление сайта не редактировались; новые комментарии в код не добавлялись.

Документация `docs/СТЕК + ФУНКЦИОНАЛ.md`, разделы 15–16, описывает отдельные каталоги `postgres-migration` и `postgres-api`, а также прямо отмечает, что статический снимок ещё подключает Supabase. В предоставленной папке этих серверных комплектов нет. Дополнительная проверка скрытых файлов и архива не обнаружила целевую схему, API или клиентский адаптер.

| Сервер | Пакет Express/pg из `postgres-api` отсутствует | Нельзя проверить JWT, роли, SQL-компилятор, refresh-сессии, загрузку файлов и API |

## Изменения в updv2

- `public/js/core/roles-engine.js`: удаление пользователя направлено на `DELETE /api/v1/auth/admin/users/:id`. Перед запросом проверяются клиентская роль admin, UUID, запрет удаления себя и наличие сессии. Успешный ответ 204 без JSON не считается ошибкой. Отказ API и сетевая ошибка не считаются успешным удалением.
- `tools/check-postgres.mjs`: добавлена отдельная проверка состава PostgreSQL-комплекта, активных legacy-подключений и наличия определений клиентских RPC в целевой схеме. Архив, зависимости и папки загрузок исключены из поиска, чтобы их копии не выдавались за рабочую реализацию.
- `tools/check-postgres-contract.mjs`: добавлены проверки клиентского DELETE-контракта, отказов доступа, отсутствующей сессии, некорректного идентификатора, сетевой ошибки и невозможности объявить комплект готовым без схемы.
- `package.json`: добавлены команды `check:postgres` и `check:postgres-contract`; зависимости не изменены.
- Этот отчёт и `docs/POSTGRES-UPDATE-FILES.json`: порядок применения и перечень файлов.

Клиентская проверка admin не заменяет авторизацию на сервере. Даже после исправления адреса API должен самостоятельно проверять токен, действующий аккаунт и роль перед удалением.

## Результаты проверки

- `npm run check`: 45 HTML-страниц и 45 собственных JavaScript-файлов, без ошибок ссылок и синтаксиса.
- `npm run check:postgres-contract`: 19 проверок прошли. HTTP-ответы воспроизведены тестовым клиентом; живой сервер не вызывался и реальные пользователи не удалялись.
- Предыдущие `check:security`: 78 проверок прошли повторно. Это регрессия legacy-слоя, не проверка автономного API.
- `npm run check:postgres`: завершился с кодом 1 и `ready: false`, как и должен при обнаруженных несоответствиях. Вывод перечисляет отсутствующие файлы и неподтверждённые RPC.

Успешная статическая проверка означает корректный синтаксис и существующие ссылки. Она не доказывает, что на сервере выполняются вход, запись в базу, отправка ботам и проверка прав.

## Применение и ограничения

Загрузите содержимое `updv2` в корень репозитория через **Add files → Upload files**, сохраняя вложенные пути. Если применяется также пакет `upd`, пакет `updv2` должен быть последним: он содержит следующую версию `roles-engine.js` и `package.json`.

Для проверки состава выполняйте `npm run check:postgres`; для проверки исправленного клиентского вызова — `npm run check:postgres-contract`. Команды не требуют подключения к рабочей базе.

**Для автономного PostgreSQL не выполняйте `database/legacy-supabase/SECURITY-HARDENING.sql` из предыдущего пакета.** Он использует Supabase `auth.uid()`, роли `anon`/`authenticated` и схему Storage. Его нельзя считать миграцией безопасности автономного портала.

Новые клиентские функции тестов `cgb_test_preview`, `cgb_start_test`, `cgb_finish_test` также нельзя считать доступными в отсутствующей целевой схеме. При подключении PostgreSQL-адаптера серверные определения и список разрешённых RPC должны соответствовать этим вызовам. Возвращать доверие к баллам, переданным браузером, для совместимости нельзя.

На основании доступных файлов нельзя исправить или проверить отсутствующий SQL-компилятор, разграничение доступа Express, хранение refresh-токенов и файловые пути сервера. Документированные списки `TABLES`, `PUBLIC_READ`, `ADMIN_TABLES` сами по себе не доказывают проверку прав на конкретную операцию: реализация должна отклонять прямые запросы обычного пользователя к чужим заявкам, жалобам, наказаниям и премиям.

Для подтверждения полного перехода нужны сами серверные исходники, целевая схема и runtime-grants. В этом этапе не создавался вымышленный API по описанию, не менялось подключение на несуществующий адаптер и не объявлялась безопасность сервера без его проверки.
